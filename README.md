Gesture-Controlled Unity Platformer
#### Video Demo:  https://youtu.be/XzaHnjd7RW8
#### Description: This project is a 2D platformer built in Unity that you control entirely with hand gestures instead of a keyboard. A webcam watches your hands, a YOLOv8 segmentation model figures out what gesture each hand is making, and that gesture gets mapped to an in-game action: moving, jumping, dashing, attacking, or quitting. The left hand handles movement and the right hand handles actions, so you're effectively using both hands like two halves of a controller, just without touching anything.

The idea started from wanting to combine two things I'd been learning separately: computer vision and game development. I'd trained small YOLO models before for basic object detection, but I hadn't tried running one live, inside a game engine, controlling gameplay in real time. That turned out to be the hard part, and most of this README is really about how I got from "model that can classify a gesture in a still image" to "model that can control a platformer without lagging or spamming inputs."

The model itself. I labeled 600 images by hand across six gesture classes: open palm, closed fist, OK, peace, point, and thumbs up. I shot these in different lighting, against different backgrounds, at different distances, and with different hands, since a model trained on one lighting setup in one room falls apart the moment you move the webcam. I used CVAT to draw polygons around each hand and convert them into pixel masks, split the data 80/20 for training and validation, and exported everything in YOLOv8-seg format. I trained four versions of the same model at different precision and resolution combinations (FP32/FP16 at 320px/640px) so the game could pick a lighter or heavier model depending on whatever hardware it's running on.

gesturecontroller.cs. This script is the bridge between the model's output and the game. Unity Sentis runs the ONNX model and hands back a tensor containing a class, an x-coordinate, and a confidence score for whatever it detected. GestureController takes the highest-confidence detection on each side of the frame (split at the midpoint, so anything left of center counts as the left hand) and maps that gesture to a function call, for example calling Attack2() when it sees "point" on the left side. It also runs on a 0.1-second buffer instead of firing every frame, because raw per-frame gesture readings jitter constantly as your hand moves, and without the buffer the game would register five gesture changes in the time it takes to actually make one gesture.

playercontroller.cs. This holds the actual gameplay functions: Jump(), MoveLeft(), MoveRight(), Attack1(), Attack2(), RollLeft(), RollRight(), StandStill(), and QuitGame(). GestureController never touches movement or physics directly, it just calls into this script, which keeps the gesture-recognition logic and the actual platforming logic separate from each other.

webcammanager.cs. This script splits the webcam feed into two paths. One copy goes into a buffer that gets fed to the YOLO model for inference. The other goes straight to the screen, so the player is always looking at a smooth live feed and never sees the model's processing overhead. Segmentation only happens on the contents of that buffer, not on what's actually displayed.

A few design choices took some back and forth to land on. Early on I tried sending frames to a separate Python server and getting predictions back as packets, which sounds reasonable until you realize the round trip adds real delay every single frame. I dropped that entirely and loaded the ONNX model directly into Unity Sentis instead, which cut out the network layer completely. I also originally ran inference every frame, which was way too expensive and introduced visible lag, so I moved to running it on a timed 0.1-second interval instead. That's a tradeoff: gestures register slightly slower than instantly, but the game stays playable, and 0.1 seconds is short enough that it doesn't feel sluggish in practice.

The other tricky problem was false positives from fast hand movement. If your hand crosses the frame quickly, the model can briefly misread the gesture. The fix was keeping both hands mostly stationary on either side of the screen, one for movement and one for actions, rather than letting the player wave a single hand around freely. That also solved a separate problem where a single moving hand couldn't do two things at once, like jumping and running in the same instant.

Finally, since inference speed on an integrated GPU was noticeably worse than on a dedicated GPU, I loaded all four exported model variants into the game at startup. The game checks the hardware and picks a sensible default, but the player can override that choice from the main menu or swap models mid-game if performance isn't holding up.
